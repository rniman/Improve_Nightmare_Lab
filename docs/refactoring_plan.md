# Refactoring Plan

이 문서는 Nightmare Lab의 점진적 리팩터링 실행 로드맵이다.
현재 정상 동작을 보존하면서 클라이언트와 서버의 치명적인 안정성 문제를 우선 처리하고,
성능 및 품질 개선은 실제 문제가 확인될 때까지 보류한다.

## 목표

- 재현되는 크래시, 데이터 손상, 연결 불안정 문제 우선 해결
- 클라이언트/서버 경계의 입력 검증과 통신 안정성 개선
- 측정된 네트워크 전송량과 전송 주기의 구조적 문제 개선
- 변경이 잦은 코드의 가독성과 책임 경계 점진 개선
- 해결된 문제와 보류된 문제를 문서에서 명확히 구분
- 정상 동작하는 렌더링 파이프라인의 불필요한 변경 방지

## 우선순위

1. 재현되는 치명적 버그와 데이터 손상 가능성
2. 네트워크 송수신 주기와 객체 수명 안정성
3. 실제 변경을 어렵게 만드는 구조적 문제
4. 문서화와 회귀 검증 기준
5. 클라이언트 및 서버 성능과 렌더링 품질 개선

## 원칙

- 기존 동작 보존을 우선한다.
- 변경은 작고 검증 가능한 단위로 유지한다.
- 문제를 재현하거나 측정한 뒤 수정한다.
- 포맷 변경과 동작 변경은 분리한다.
- 인코딩 및 라인엔딩 변경은 별도 커밋으로 분리한다.
- 레거시 코드는 실제로 수정하는 범위부터 컨벤션을 적용한다.
- 큰 클래스나 raw pointer가 있다는 이유만으로 작업을 만들지 않는다.
- 디렉토리 재구성은 모듈 경계가 안정된 뒤 별도 작업으로 수행한다.
- 렌더링 최적화는 프레임 문제가 확인되고 기준선이 확보된 뒤 진행한다.
- 외부 및 자동 생성 파일은 수정하지 않는다:
  `d3dx12.h`, `DDSTextureLoader12.*`, `Resource.h`, `targetver.h`.

## 현재 상태

### 완료

- 클라이언트 시작, 씬 전환, 인게임 렌더링 흐름을 다시 확인했다.
- 좀비 플레이어 단독 접속 시 발생하던 조명 및 SSAO 문제를 수정했다.
- SSAO를 `Disabled`, `Raw`, `Blurred` 세 상태로 전환할 수 있게 했다.
- SSAO 블러 반경을 조정해 얼룩 현상을 완화했다.
- `CScene`, `CLobbyScene`, `CMainScene`의 접근 범위와 선언 순서를 정리했다.
- `Scene.cpp`의 멤버 함수 정의 순서를 헤더 선언 순서에 맞췄다.
- command list를 `Reset()`한 직후 공통 root signature와 descriptor heap을 설정하도록 정리했다.
- 네트워크 연결 종료 경로를 통합하고 TCP partial recv/send 진행 상태를 소켓별로 보존하도록 수정했다.
- 애플리케이션 송신 요청과 Winsock `FD_WRITE` 알림을 분리하고 송신 큐 처리를 통합했다.
- 서버는 클라이언트 패킷 head, slot, key mask, transform을 검증한 뒤 상태에 적용한다.
- 클라이언트는 서버 패킷 head, 크기, client/object ID, 개수, transform을 검증한 뒤 상태에 적용한다.
- 서버 네트워크 통계를 연결별·패킷 head별 전송량, 큐 최고치, `WOULDBLOCK` 횟수로 측정할 수 있게 했다.
- 네트워크 패킷 상태 표현과 이벤트·진단 처리 책임을 정리했다.
- partial I/O 안정화 변경 당시 Client/Server x64 Debug 빌드와 서버 실행을 확인했고,
  현재 코드의 Release 서버 1인 접속 실행을 확인했다.

### 우선 확인 대상

- 입력 송신을 렌더 루프 밖의 고정 주기로 옮길 필요가 있는지 조작감과 낮은 FPS 조건에서 판단한다.
- 상태 복제 60 Hz가 다중 접속과 느린 네트워크에서도 유지되는지 검증한다.
- TCP partial send/recv와 `WOULDBLOCK`을 강제로 발생시키는 부하 조건에서 재개 경로를 검증한다.
- 씬 전환과 연결 종료 경로에서 객체 및 네트워크 상태 수명을 확인한다.
- 렌더 리소스의 소유권과 command list 상태 변경이 기존 동작을 보존하는지 확인한다.

### 변경 전 네트워크 측정 기준선

2026-08-18 Release 서버에 클라이언트 1명이 접속한 상태에서 1초 구간을 측정했다.
통계의 byte 수는 TCP/IP 헤더를 제외한 애플리케이션 데이터량이다.

- `KEYS_BUFFER`: 패킷당 131 byte, 초당 141~144 packet, 약 18.5~18.9 KB/s 수신
- `UPDATE_DATA`: 패킷당 10,701 byte, 초당 141~144 packet, 약 1.51~1.54 MB/s 송신
- 송신 큐: 측정 시점 0 byte/0 packet, 연결별 최고치 10,701 byte/1 packet
- `UPDATE_DATA` 전송 횟수가 Release 클라이언트의 프레임 빈도와 거의 일치한다.

현재 큐가 비어 있다는 사실은 전송량이 적다는 의미가 아니라, 1인 로컬 조건에서 생성된
패킷을 즉시 전송할 수 있었다는 의미다. 다중 접속이나 느린 네트워크 조건에서는 같은
구조가 서버 송신량과 큐 적체를 확대할 수 있다.

### 구현 1 이후 네트워크 측정

2026-08-19 Release 서버의 클라이언트 1명 접속 상태에서 다음 값이 측정됐다.

- `UPDATE_DATA`: 패킷당 10,701 byte, 초당 60 packet, 642,060 byte/s 송신
- `KEYS_BUFFER`: 패킷당 131 byte, 초당 48 packet, 6,288 byte/s 수신
- 이벤트 패킷: 문 열기/닫기 이벤트가 일반 상태 복제와 별도로 즉시 전송됨
- 송신 큐: 0 byte/0 packet, 연결별 최고치 10,701 byte/1 packet
- `WOULDBLOCK`: TX 0회, RX 구간별 0~2회이며 수신은 정상 재개됨

서버 상태 복제는 입력 수신 빈도 48 Hz와 무관하게 목표한 60 Hz를 유지했다. 반면 클라이언트
입력은 `ProcessInput()`에서 주기 함수를 호출하므로 60 Hz 상한은 적용됐지만 측정 당시
프레임 호출 조건에서 48 Hz에 머물렀다. 입력을 반드시 고정 60 Hz로 보낼 필요가 있는지는 별도 작업으로 판단한다.

### 보류

- shadow map 렌더링 횟수 및 대상 조명 수 최적화
- SSAO, post-processing, blur compute의 GPU 시간 측정
- SSAO와 그림자 품질 개선
- `WaitForGpuComplete`와 프레임 동기화 최적화
- D2D text UI 및 readback 성능 분석
- 서버 tick 시간 및 전체 상태 복제량 최적화
- 렌더링 파이프라인 대규모 재설계

## Phase 0. 현재 기준선 정리 — 완료

- 클라이언트 실행과 씬 전환 흐름을 확인했다.
- shadow, deferred/post-processing, SSAO, blur, forward/UI 흐름을 추적했다.
- 좀비 단독 접속 조명 문제의 재현 조건을 확인하고 수정했다.
- Scene 클래스 구조와 공통 command list 상태 설정을 정리했다.
- 빌드 및 실행 기준선을 확인했다.

이 단계의 렌더링 성능 수치는 필수 기준선으로 사용하지 않는다.
현재 프레임 문제가 재현되지 않으므로 상세 GPU 측정은 Phase 5로 보류한다.

## Phase 1. 치명적 안정성 문제 점검

- 클라이언트와 서버의 외부 입력, 배열 인덱스, 패킷 크기 범위 검증은 핵심 경로에 적용했다.
- TCP partial send/recv와 연결 종료 처리가 데이터를 잃거나 미완성 패킷을 적용하지 않는지 확인한다.
- player, light camera, object 참조의 유효 범위를 확인한다.
- 씬 전환, 연결 종료, 렌더 리소스 해제 중 null 접근 및 수명 문제를 확인한다.
- 재현 가능한 문제를 발견한 경우에만 최소 범위로 수정한다.

## Phase 2. 네트워크 송수신 안정화

핵심 코드 변경은 완료했다. 기존 패킷 포맷과 `WSAAsyncSelect` 구조를 유지하면서
연결 종료 통합, partial recv 누적, 소켓별 송신 큐 및 실제 `FD_WRITE` 재개 경로를 적용했다.
이후 서버·클라이언트 입력 검증과 네트워크 진단 통계도 적용했다.
남은 안정성 작업은 다중 접속 및 네트워크 부하 조건의 회귀 검증이다.

- 소켓별 수신 진행 상태를 유지하고 완성된 패킷만 해석한다.
- partial send와 `WOULDBLOCK`에서 남은 데이터를 보존하고 이후 `FD_WRITE`에서 재개한다.
- 애플리케이션의 송신 요청과 Winsock의 쓰기 가능 알림을 구분한다.
- 연결 수락 실패, 인게임 중 접속 거부, 연결 종료 시 슬롯과 객체 상태를 일관되게 정리한다.
- 패킷 포맷 변경 없이 적용할 수 있는 작은 수정부터 수행한다.

소켓별 송신 큐는 적용됐으며, 큐 병합이나 우선순위 같은 추가 정책은 실제 적체를
측정한 뒤 별도 작업으로 정한다.
IOCP 전환이나 서버 다중 스레드화는 현재 범위에 포함하지 않는다.

## Phase 2.1. 입력 응답과 상태 복제 주기 분리 — 1인 검증 완료

변경 전 클라이언트는 인게임 렌더 프레임마다 `KEYS_BUFFER`를 전송하고, 서버는 완성된
클라이언트 패킷을 처리한 뒤 `RequestSend()`를 호출했다. 일반 상태에서는 이 호출이
10,701 byte의 `UPDATE_DATA` 응답으로 이어지므로 렌더 FPS가 송수신 빈도를 결정한다.

기존 wire 패킷 포맷을 유지한 채 다음 전송 트리거 분리를 적용했다.

- 클라이언트는 매 프레임 최신 입력을 갱신하되 `SendInputIfDue()`에서 최대 60 Hz로 전송한다. 호출점이 렌더 루프이므로 FPS가 60보다 낮으면 입력 빈도도 함께 낮아진다.
- 서버는 `KEYS_BUFFER` 수신에 `UPDATE_DATA`로 응답하지 않고 `ReplicateStateIfDue()`에서 최대 60 Hz로 최신 상태를 전송한다.
- 모든 활성 클라이언트의 로딩 완료 이후에만 상태 복제를 시작한다.
- 입력은 마지막 수신 상태를 다음 입력이 올 때까지 유지하는 현재 서버 동작을 보존한다.
- 게임 종료, 사운드, 로딩 완료, 영역 이탈과 같은 이벤트 패킷은 즉시 전송한다.
- 프레임이나 메시지 처리가 지연돼도 놓친 주기만큼 패킷을 몰아서 보내지 않는다.
- 오래된 `UPDATE_DATA`가 큐에 누적되는지 측정하고, 필요할 때에만 latest-only 병합을 별도 적용한다.
- 60 FPS 이상 조건에서 입력이 상한을 넘지 않는지, 낮은 FPS에서 입력 빈도와 조작감이 허용 가능한지 비교한다.

첫 Release 1인 검증에서 서버 상태 복제는 60 Hz, 클라이언트 입력은 프레임 호출 조건에 따라
48 Hz로 측정됐다. 입력과 상태 응답의 결합 제거 및 서버 60 Hz 복제 목표는 확인됐으며,
다중 접속 검증 전까지 전체 복제 위험은 유지한다. 실제 조작감과 전송량을 확인한 뒤 원격
플레이어 보간을 추가하고 상태 복제를 30 Hz로 낮추는 작업을 분리한다.
주기 분리 후에도 패킷당
10,701 byte가 병목이면 비활성 슬롯 제외, 플레이어 상태와 오브젝트 상태 분리,
변경된 오브젝트만 직렬화하는 작업을 별도 패킷 포맷 변경으로 계획한다.

## Phase 3. 문제 목록과 기술 부채 관리

- `docs/code_smells.md`에 문제를 `Bug`, `Risk`, `Maintainability`,
  `Deferred`, `Resolved`로 분류한다.
- 각 항목에 실제 근거, 영향 범위, 다음 확인 방법을 기록한다.
- 재현 근거가 없는 항목은 버그가 아니라 위험 또는 보류 항목으로 관리한다.
- 해결된 문제는 삭제하지 않고 검증 결과와 함께 `Resolved`로 이동한다.
- 작업을 시작할 때 해당 항목을 하나의 작은 커밋 단위로 구체화한다.

## Phase 4. 문제 기반의 작은 구조 개선

- 실제 변경이 필요한 경로에서만 `GameFramework` 책임을 작은 함수로 분리한다.
- `Scene`과 `TCPClient`의 직접 의존을 점진적으로 완화한다.
- 네트워크 패킷 파싱과 게임 상태 적용을 분리한다.
- 소유권이나 수명이 불명확해 실제 위험이 있는 리소스부터 정리한다.
- 헤더가 PCH 또는 다른 헤더의 간접 include에 의존하지 않도록, 실제로 수정하는 모듈부터 필요한 표준·외부 헤더를 직접 include한다.
- 이미 정리된 Scene 선언 구조는 추가 변경보다 안정화를 우선한다.
- public API 변경과 대규모 클래스 분리는 별도 승인된 작업으로 진행한다.

include 의존성 정리는 동작 변경이나 전체 헤더 일괄 수정과 분리해 작은 커밋으로 진행한다.

## Phase 5. 보류된 성능 및 품질 개선

다음 항목은 프레임 저하, 서버 부하, 시각적 결함 또는 기능 요구가 확인될 때 재개한다.

- shadow map 렌더링 횟수와 조명 선택 최적화
- SSAO 및 blur 패스별 GPU 시간 측정
- SSAO 및 그림자 필터링 품질 개선
- `WaitForGpuComplete`, `MoveToNextFrame` 동기화 개선
- D2D text UI와 readback 비용 분석
- 렌더링 옵션 및 품질 단계 추가
- 활성 클라이언트 수별 server tick 시간 측정과 고정 tick 검토

- 신규 렌더링 프레임워크 또는 외부 라이브러리 도입

## 검증 기준

- Client와 Server가 대상 구성에서 빌드되어야 한다.
- 서버 접속, 로비 진입, 게임 시작, 종료 흐름이 유지되어야 한다.
- 네트워크 변경은 패킷 크기, 전송 빈도, 연결 상태를 비교할 수 있어야 한다.
- 네트워크 주기 변경 후 렌더 FPS가 달라도 입력·상태 패킷 빈도가 설정값 범위에 있어야 한다.
- 버그 수정은 재현 조건과 수정 후 결과를 기록해야 한다.
- 성능 개선은 변경 전후 측정값이 있을 때만 완료로 판단한다.
- `architecture.md`, `pipeline.md`, `code_smells.md`와 문서 역할이 겹치지 않아야 한다.
- 각 작업은 독립적으로 검토하고 되돌릴 수 있는 커밋 단위여야 한다.
