# Refactoring Plan

이 문서는 Nightmare Lab의 점진적 리팩터링 실행 로드맵이다.
현재 정상 동작을 보존하면서 클라이언트와 서버의 치명적인 안정성 문제를 우선 처리하고,
성능 및 품질 개선은 실제 문제가 확인될 때까지 보류한다.

## 목표

- 재현되는 크래시, 데이터 손상, 연결 불안정 문제 우선 해결
- 클라이언트/서버 경계의 입력 검증과 통신 안정성 개선
- 측정된 네트워크 전송량과 전송 주기의 구조적 문제 개선
- 변경이 잦은 코드의 가독성과 책임 경계 점진 개선
- 해결된 문제와 보류된 문제를 문서에서 명확히 구분
- 정상 동작하는 렌더링 파이프라인의 불필요한 변경 방지

## 우선순위

1. 재현되는 치명적 버그와 데이터 손상 가능성
2. 네트워크 송수신 주기와 객체 수명 안정성
3. 실제 변경을 어렵게 만드는 구조적 문제
4. 문서화와 회귀 검증 기준
5. 클라이언트 및 서버 성능과 렌더링 품질 개선

## 원칙

- 기존 동작 보존을 우선한다.
- 변경은 작고 검증 가능한 단위로 유지한다.
- 문제를 재현하거나 측정한 뒤 수정한다.
- 포맷 변경과 동작 변경은 분리한다.
- 인코딩 및 라인엔딩 변경은 별도 커밋으로 분리한다.
- 레거시 코드는 실제로 수정하는 범위부터 컨벤션을 적용한다.
- 큰 클래스나 raw pointer가 있다는 이유만으로 작업을 만들지 않는다.
- 디렉토리 재구성은 모듈 경계가 안정된 뒤 별도 작업으로 수행한다.
- 렌더링 최적화는 프레임 문제가 확인되고 기준선이 확보된 뒤 진행한다.
- 외부 및 자동 생성 파일은 수정하지 않는다:
  `d3dx12.h`, `DDSTextureLoader12.*`, `Resource.h`, `targetver.h`.

## 현재 상태

### 완료

- 클라이언트 시작, 씬 전환, 인게임 렌더링 흐름을 다시 확인했다.
- 좀비 플레이어 단독 접속 시 발생하던 조명 및 SSAO 문제를 수정했다.
- SSAO를 `Disabled`, `Raw`, `Blurred` 세 상태로 전환할 수 있게 했다.
- SSAO 블러 반경을 조정해 얼룩 현상을 완화했다.
- `CScene`, `CLobbyScene`, `CMainScene`의 접근 범위와 선언 순서를 정리했다.
- `Scene.cpp`의 멤버 함수 정의 순서를 헤더 선언 순서에 맞췄다.
- command list를 `Reset()`한 직후 공통 root signature와 descriptor heap을 설정하도록 정리했다.
- 네트워크 연결 종료 경로를 통합하고 TCP partial recv/send 진행 상태를 소켓별로 보존하도록 수정했다.
- 애플리케이션 송신 요청과 Winsock `FD_WRITE` 알림을 분리하고 송신 큐 처리를 통합했다.
- 서버는 클라이언트 패킷 head, slot, key mask, transform을 검증한 뒤 상태에 적용한다.
- 클라이언트는 서버 패킷 head, 크기, client/object ID, 개수, transform을 검증한 뒤 상태에 적용한다.
- 서버 네트워크 통계를 연결별·패킷 head별 전송량, 큐 최고치, `WOULDBLOCK` 횟수로 측정할 수 있게 했다.
- 네트워크 패킷 상태 표현과 이벤트·진단 처리 책임을 정리했다.
- 클라이언트 입력의 고FPS 과다 송신을 막고 서버 상태 복제를 입력 응답에서 분리해 각각 최대 60 Hz로 제한했다.
- 고정 10,701 byte `UPDATE_DATA`를 `PLAYER_STATE` 60 Hz와 수신자별 가변 길이
  `NEARBY_OBJECTS` 30 Hz로 분리하고 legacy 패킷을 제거했다.
- 문·서랍을 `NEARBY_OBJECTS`에서 제외하고 상태 변경 event, 로딩 완료 snapshot과
  클라이언트 프레임 애니메이션으로 동기화했다.
- 게임 시작 후 마지막 플레이어가 연결을 종료하면 서버가 정상 종료되도록 했다.
- partial I/O 안정화 변경 당시 Client/Server x64 Debug 빌드와 서버 실행을 확인했고,
  상태 복제 변경은 Release 로컬 1~3인 접속, 상호작용, 승패와 종료 흐름을 확인했다.
- `TCPServer`의 이름, 선언/정의 순서와 기능별 함수 구역을 정리하고 초기화를
  `InitializeNetworking()`과 `InitializeWorld()`로 분리했다.
- 서버 씬 로딩, 프레임별 오브젝트 생성, 탈출문 선택과 초기 아이템 배치를
  `ServerWorldBuilder`로 옮기고 `mDrawerEntries`도 빌더 내부 상태로 이동했다.
- 런타임에서 얻은 클라이언트·플레이어·스폰 인덱스를 접근 직전에 검증하도록 정리했다.
- 최신 서버 구조 변경을 대상 구성으로 빌드하고, 서버 시작·월드 생성·게임 시작 흐름을 실행 확인했다.
- 월드 구성을 네트워크 초기화보다 먼저 수행하고, `ServerWorldBuilder` 실패를
  `TCPServer::Initialize()`의 실패 결과로 전달하도록 정리했다.
- `ServerScene.bin`이 없는 작업 디렉터리에서 서버를 실행해 파일 열기 오류가 출력되고
  리슨 소켓을 열기 전에 프로세스가 종료되는 실패 경로를 확인했다.

### 현재 활성 단계

- Phase 4의 클라이언트 의존성 개선을 작은 변경 단위로 진행한다.
- 첫 후보는 `MAX_CLIENT` 정의 위치를 정리해 `Scene.h`가 `TCPClient.h`를 포함하지 않게 하는 작업이다.
- 다음 후보는 `TCPClient.cpp`가 `CGameFramework::GetKeysBuffer()`를 직접 호출하는 역의존을
  입력 스냅샷 전달 방식으로 완화하는 작업이다.
- 패킷 파싱과 게임 상태 적용 분리는 실제 수정이 필요한 클라이언트 패킷부터 한 종류씩 진행한다.
- 씬 전환·연결 종료 수명과 렌더 리소스 상태는 관련 코드를 수정할 때마다 회귀 검증한다.

### 후속 검증 backlog — 현재 보류

- 입력 송신을 렌더 루프 밖의 고정 주기로 옮기는 작업은 낮은 FPS에서 조작 문제가 재현될 때 검토한다.
- 5인·느린 네트워크의 장시간 큐 검증과 강제 partial I/O 테스트는 현재 네트워크 구현을
  변경하지 않고 보류한다. 큐 증가, 전송 주기 불안정 또는 연결 문제가 관찰되면 재개한다.
- 활성 클라이언트 수별 서버 tick 시간과 CPU 사용률 측정은 tick 지연이나 CPU 문제가
  관찰될 때 재개한다.

### 변경 전 네트워크 측정 기준선

2026-08-18 Release 서버에 클라이언트 1명이 접속한 상태에서 1초 구간을 측정했다.
통계의 byte 수는 TCP/IP 헤더를 제외한 애플리케이션 데이터량이다.

- `KEYS_BUFFER`: 패킷당 131 byte, 초당 141~144 packet, 약 18.5~18.9 KB/s 수신
- `UPDATE_DATA`: 패킷당 10,701 byte, 초당 141~144 packet, 약 1.51~1.54 MB/s 송신
- 송신 큐: 측정 시점 0 byte/0 packet, 연결별 최고치 10,701 byte/1 packet
- `UPDATE_DATA` 전송 횟수가 Release 클라이언트의 프레임 빈도와 거의 일치한다.

현재 큐가 비어 있다는 사실은 전송량이 적다는 의미가 아니라, 1인 로컬 조건에서 생성된
패킷을 즉시 전송할 수 있었다는 의미다. 다중 접속이나 느린 네트워크 조건에서는 같은
구조가 서버 송신량과 큐 적체를 확대할 수 있다.

### 구현 1 이후 네트워크 측정

2026-08-19 Release 서버의 클라이언트 1명 접속 상태에서 다음 값이 측정됐다.

- `UPDATE_DATA`: 패킷당 10,701 byte, 초당 60 packet, 642,060 byte/s 송신
- `KEYS_BUFFER`: 패킷당 131 byte, 초당 48 packet, 6,288 byte/s 수신
- 이벤트 패킷: 문 열기/닫기 이벤트가 일반 상태 복제와 별도로 즉시 전송됨
- 송신 큐: 0 byte/0 packet, 연결별 최고치 10,701 byte/1 packet
- `WOULDBLOCK`: TX 0회, RX 구간별 0~2회이며 수신은 정상 재개됨

같은 Release 환경의 클라이언트 2명 접속에서는 `UPDATE_DATA`가 연결당 60 packet/s,
총 120 packet/s와 1,284,120 byte/s로 측정됐다. 각 연결의 송신 큐는 0 byte/0 packet을
유지했으며, 게임 종료 시 WIN 패킷이 전송되는 로그도 확인했다.

초기 구현은 다음 입력 deadline을 매번 현재 시각에서 다시 잡아 프레임별 초과 시간을
버렸다. 그 결과 60 FPS에서 37~39 packet/s, 144 FPS에서 48~49 packet/s, 무제한 FPS에서
54~56 packet/s로 측정됐다. deadline을 기존 기준 시각에서 경과 주기 수만큼 전진시키도록
보정한 뒤 60/144/무제한 FPS에서 `KEYS_BUFFER`가 60 packet/s를 유지했다. 30 FPS에서는
렌더 루프에서 호출할 수 있는 상한에 따라 30 packet/s가 측정됐다.

로컬 Release 클라이언트 3명 접속에서는 `UPDATE_DATA`가 연결당 60 packet/s, 총
180 packet/s와 1,926,180 byte/s로 측정됐다. 모든 연결의 송신 큐와 TX `WOULDBLOCK`은
0이었고, `OPEN_DRAWER_SOUND`가 일반 상태 복제와 별도 패킷으로 전송됐다. 클라이언트별
입력은 테스트 PC에서 실제로 확보된 프레임에 따라 48, 60, 49 packet/s였다. 5인 실행은
단일 테스트 PC의 렌더링 자원 한계로 수행하지 못했으므로 최대 인원 검증은 남겨 둔다.

## Phase 0. 현재 기준선 정리 — 완료

- 클라이언트 실행과 씬 전환 흐름을 확인했다.
- shadow, deferred/post-processing, SSAO, blur, forward/UI 흐름을 추적했다.
- 좀비 단독 접속 조명 문제의 재현 조건을 확인하고 수정했다.
- Scene 클래스 구조와 공통 command list 상태 설정을 정리했다.
- 빌드 및 실행 기준선을 확인했다.

이 단계의 렌더링 성능 수치는 필수 기준선으로 사용하지 않는다.
현재 프레임 문제가 재현되지 않으므로 상세 GPU 측정은 Phase 5로 보류한다.

## Phase 1. 치명적 안정성 문제 점검

- 클라이언트와 서버의 외부 입력, 배열 인덱스, 패킷 크기 범위 검증은 핵심 경로에 적용했다.
- TCP partial send/recv와 연결 종료 처리가 데이터를 잃거나 미완성 패킷을 적용하지 않는지 확인한다.
- player, light camera, object 참조의 유효 범위를 확인한다.
- 씬 전환, 연결 종료, 렌더 리소스 해제 중 null 접근 및 수명 문제를 확인한다.
- 재현 가능한 문제를 발견한 경우에만 최소 범위로 수정한다.

## Phase 2. 네트워크 송수신 안정화

핵심 코드 변경은 완료했다. 기존 패킷 포맷과 `WSAAsyncSelect` 구조를 유지하면서
연결 종료 통합, partial recv 누적, 소켓별 송신 큐 및 실제 `FD_WRITE` 재개 경로를 적용했다.
이후 서버·클라이언트 입력 검증과 네트워크 진단 통계도 적용했다.
남은 안정성 작업은 다중 접속 및 네트워크 부하 조건의 회귀 검증이다.

- 소켓별 수신 진행 상태를 유지하고 완성된 패킷만 해석한다.
- partial send와 `WOULDBLOCK`에서 남은 데이터를 보존하고 이후 `FD_WRITE`에서 재개한다.
- 애플리케이션의 송신 요청과 Winsock의 쓰기 가능 알림을 구분한다.
- 연결 수락 실패, 인게임 중 접속 거부, 연결 종료 시 슬롯과 객체 상태를 일관되게 정리한다.
- 패킷 포맷 변경 없이 적용할 수 있는 작은 수정부터 수행한다.

소켓별 송신 큐는 적용됐으며, 큐 병합이나 우선순위 같은 추가 정책은 실제 적체를
측정한 뒤 별도 작업으로 정한다.
IOCP 전환이나 서버 다중 스레드화는 현재 범위에 포함하지 않는다.

## Phase 2.1. 입력 응답과 상태 복제 주기 분리 — 로컬 3인 검증 완료

변경 전 클라이언트는 인게임 렌더 프레임마다 `KEYS_BUFFER`를 전송하고, 서버는 완성된
클라이언트 패킷을 처리한 뒤 `EnqueuePendingPacket()`를 호출했다. 일반 상태에서는 이 호출이
10,701 byte의 `UPDATE_DATA` 응답으로 이어지므로 렌더 FPS가 송수신 빈도를 결정한다.

기존 wire 패킷 포맷을 유지한 채 다음 전송 트리거 분리를 적용했다.

- 클라이언트는 매 프레임 최신 입력을 갱신하되 `SendInputIfDue()`에서 최대 60 Hz로 전송한다. 호출점이 렌더 루프이므로 FPS가 60보다 낮으면 입력 빈도도 함께 낮아진다.
- 서버는 `KEYS_BUFFER` 수신에 `UPDATE_DATA`로 응답하지 않고 `ReplicateStateIfDue()`에서 최대 60 Hz로 최신 상태를 전송한다.
- 모든 활성 클라이언트의 로딩 완료 이후에만 상태 복제를 시작한다.
- 입력은 마지막 수신 상태를 다음 입력이 올 때까지 유지하는 현재 서버 동작을 보존한다.
- 게임 종료, 사운드, 로딩 완료, 영역 이탈과 같은 이벤트 패킷은 즉시 전송한다.
- 프레임이나 메시지 처리가 지연돼도 놓친 주기만큼 패킷을 몰아서 보내지 않는다.
- 오래된 `UPDATE_DATA`가 큐에 누적되는지 측정하고, 필요할 때에만 latest-only 병합을 별도 적용한다.
- 60 FPS 이상 조건에서 입력이 상한을 넘지 않는지, 낮은 FPS에서 입력 빈도와 조작감이 허용 가능한지 비교한다.

입력 deadline 보정 후 Release 60/144/무제한 FPS에서는 입력과 상태 복제가 각각 60 Hz를
유지했고, 30 FPS 입력은 렌더 루프 상한에 따라 30 Hz였다. 로컬 3인에서도 상태 복제는
연결당 60 Hz, 큐 0을 유지했다. 5인은 단일 테스트 PC의 렌더링 부하로 미검증이지만,
접속자 증가에 따른 상태 송신량은 1~3인 측정에서 연결 수에 비례해 선형 증가했다.

## Phase 2.2. 플레이어 상태와 오브젝트 상태 복제 분리 — 구현 및 Release 검증 완료

필드별 생성·소비 경로를 조사했으며, 첫 구현에서는 용도가 확인된
필드를 한꺼번에 제거하지 않고 플레이어 상태와 오브젝트 상태의 책임
경계부터 분리했다.

원격 플레이어 보간과 전체 상태 30 Hz 전환은 우선 적용하지 않는다. 보간은 표시 지연을
추가하면서도 분리 전 10,701 byte 고정 패킷의 근본 원인을 제거하지 못한다. 당시
플레이어 한 명분 2,140 byte 중 주변 오브젝트 ID 30개와 4x4 행렬 30개가
2,040 byte를 차지한다. 최대 5명분에서는 약 10,200 byte로 전체 payload의 약 95%다.
플레이어 상태 자체는 최대 5명분 약 500 byte다.

네트워크 복제용 주변 조사는 공간 이탈 즉시 이벤트와 책임을 분리했고,
`steady_clock` 기준 독립 30 Hz로 제한했다. 게임플레이 충돌·상호작용 조사와
공간 이탈 패킷은 매 시뮬레이션에서 계속 처리한다. 플레이어 상태는
오브젝트 배열을 제외한 `PLAYER_STATE`로 60 Hz 분리했다. 주변
오브젝트는 수신자 자신의 3x3 셀을 기준으로 중복 ID를 제거한 뒤
실제 개수만 `NEARBY_OBJECTS`로 30 Hz 전송한다.

가장 작은 단계부터 다음 순서로 진행한다.

1. 플레이어 위치·속도·방향·생존·아이템 상태만 담는 작은 패킷을 60 Hz로 분리한다. — 구현, 1인 실행 확인
2. 주변 오브젝트는 실제 개수만 담는 가변 길이 패킷으로 분리하고 초기 주기는 30 Hz로 둔다. — 구현, Release 2인 실행 확인
3. 모든 플레이어의 고정 배열을 모든 연결에 보내지 않고 해당 클라이언트의 관심 영역을 기준으로 전송한다. — 구현, Release 2인 실행 확인
4. 같은 오브젝트가 여러 셀에 포함되면 ID 기준으로 중복을 제거한다. — 구현, Release 2인 실행 확인
5. 공간 이탈, 사운드, 승패 같은 기존 이벤트 패킷은 즉시 전송 경로를 유지한다.
6. 새 경로를 기존 `UPDATE_DATA`와 비교 검증한 뒤 legacy head와 고정 오브젝트 배열을 제거한다. — 구현, Release 1·2인 실행 확인
7. C→S 입력에서 서버가 소비하지 않는 상태 echo와 중복 `KEY_RBUTTON` bit를 제거하고 right-click action만 전달하며, S→C 상태에서 미사용 right-click 필드를 제거한다. — 구현, Release 1인 주기·크기 확인

현재 `PLAYER_STATE`는 header 포함 461 byte이며 60 Hz에서 클라이언트당
27,660 byte/s 또는 약 0.221 Mbps다. `NEARBY_OBJECTS`는 오브젝트 30개
최대 조건에서 2,043 byte이고 30 Hz에서 61,290 byte/s 또는 약
0.490 Mbps다. 애플리케이션 데이터 기준 S→C 합계는 최대 약 0.712 Mbps로
예상한다. 실제 개수, 중복 제거,
TCP/IP 오버헤드에 따라 달라진다. Release 2인 측정에서는 서버 전체 송신이
78,436~84,964 byte/s였으며, 실제 관심 영역 오브젝트 수가 최대 30개보다 적어
예상 최대치보다 크게 낮았다.

Release 로컬 3인 최종 측정에서 서버 TX는 평균 94,067 byte/s였다. 변경 전
`2092acd2`의 동일한 3인 조건 평균 2,743,023 byte/s와 비교하면 96.57% 감소한
수치다. 출력 시점 송신 큐는 계속 0 byte/0 packet이었고 연결별 구간 peak는
최대 461 byte/1 packet이었다.

## Phase 2.3. 문·서랍 상태 동기화 분리 — 구현 및 Release 검증 완료

문·서랍은 주기적인 `NEARBY_OBJECTS` 행렬 복제에서 제외했다. 서버에서 상태가
변경되면 ID, 타입과 open/close 상태를 `OPENABLE_OBJECT_STATE`로 모든 활성
클라이언트에 즉시 전달한다. 모든 클라이언트의 로딩이 완료되면 현재 상태 전체를
`OPENABLE_OBJECT_SNAPSHOT`으로 한 번 전달해 초기 상태도 수렴시킨다.

클라이언트는 toggle 명령이 아니라 서버의 최종 상태를 `ApplyAuthoritativeState()`로
적용하고 렌더 프레임마다 문·서랍 애니메이션을 진행한다. 서버의 기존 행렬 업데이트와
충돌 판정 권위는 유지한다. Release 실행에서 자신과 다른 클라이언트의 문·서랍 상태,
서랍 애니메이션, 상호작용과 게임 종료 흐름을 확인했다.

### 후속 서버 검증 및 최적화 보류 판단

현재 측정에서 큐 증가나 주기 불안정이 없고 1인 실제 서버 송신은 약 0.287 Mbps다.
최대 30개 조건의 5인 이론값도 애플리케이션 데이터 기준 약 3.56 Mbps이므로,
추가 대역폭 압축과 서버 부하 작업은 여기서 중단한다. 다음 항목은 현재 backlog로
보존하고, 관찰 가능한 문제가 생길 때 다음 순서로 재개한다.

1. 5인 또는 렌더링 없는 더미 클라이언트와 느린 네트워크에서 장시간 Queue·주기 검증
2. 강제 partial I/O와 `WOULDBLOCK` 조건에서 송수신 재개 경로 검증
3. tick 지연이나 CPU 문제가 관찰될 경우 활성 클라이언트 수별 서버 tick 시간과 CPU 사용률 측정
4. 구조체 padding과 빌드 설정 의존을 제거하는 필드 단위 wire 직렬화·protocol version
5. 실제 profiler나 큐 증가가 확인될 때만 송신 buffer pool, latest-only, 30 Hz 플레이어 보간 검토

활성 플레이어 가변 전송, delta snapshot, transform 압축과 카메라 컬링은 현재 규모에서
복잡성 대비 이득이 작으므로 보류한다. 주변 오브젝트 30개 제한 도달, 서버 tick 저하,
WAN 환경의 움직임 끊김 중 하나가 측정될 때 재평가한다.

원격 플레이어 보간은 작은 플레이어 상태 패킷을 30 Hz 이하로 낮출 필요가 있거나 실제
원격 움직임 끊김이 확인될 때 별도 단계로 재검토한다. 로컬 플레이어 예측도 조작 지연이
측정되기 전에는 추가하지 않는다.

## Phase 3. 문제 목록과 기술 부채 관리

- `docs/code_smells.md`에 문제를 `Bug`, `Risk`, `Maintainability`,
  `Deferred`, `Resolved`로 분류한다.
- 각 항목에 실제 근거, 영향 범위, 다음 확인 방법을 기록한다.
- 재현 근거가 없는 항목은 버그가 아니라 위험 또는 보류 항목으로 관리한다.
- 해결된 문제는 삭제하지 않고 검증 결과와 함께 `Resolved`로 이동한다.
- 작업을 시작할 때 해당 항목을 하나의 작은 커밋 단위로 구체화한다.

## Phase 4. 문제 기반의 작은 구조 개선 — 현재 활성 단계

- `MAX_CLIENT`의 정의 위치를 정리해 `Scene.h`의 `TCPClient.h` 직접 include를 제거한다.
- `GameFramework.h`에서는 가능한 타입을 전방 선언하고 구현에 필요한 헤더는 `.cpp`에서 직접 include한다.
- `TCPClient.cpp`가 `CGameFramework`의 정적 입력 버퍼를 직접 조회하는 역의존을 입력 스냅샷 전달로 점진적으로 완화한다.
- 네트워크 패킷 파싱과 게임 상태 적용은 실제 수정이 필요한 클라이언트 패킷부터 한 종류씩 분리한다.
- 실제 변경이 필요한 경로에서만 `GameFramework` 책임을 작은 함수로 분리한다.
- 소유권이나 수명이 불명확해 실제 위험이 있는 리소스부터 정리한다.
- 헤더가 PCH 또는 다른 헤더의 간접 include에 의존하지 않도록, 실제로 수정하는 모듈부터 필요한 표준·외부 헤더를 직접 include한다.
- 이미 정리된 Scene 선언 구조는 추가 변경보다 안정화를 우선한다.
- public API 변경과 대규모 클래스 분리는 별도 승인된 작업으로 진행한다.

include 의존성 정리는 동작 변경이나 전체 헤더 일괄 수정과 분리해 작은 커밋으로 진행한다.

### TCPServer 점진적 책임 분리 상태

- 완료: 수명주기 함수 분리, 네트워크 통계 분리, 월드 구성을 `ServerWorldBuilder`로 분리.
- 유지: `TCPServer`는 Win32 소켓 이벤트와 서버 시뮬레이션의 최상위 오케스트레이터다.
- 남음: 패킷 역직렬화와 상태 적용, 연결/송신 큐, 상태 복제, 게임 세션 책임이
  `TCPServer` 내부에 함께 있다.
- 현재 상태: 서버 부하 및 추가 책임 분리는 보류한다.
- 재개 순서: 서버 변경 필요가 생기면 패킷 역직렬화 경계를 먼저 분리하고, 실제 변경 빈도와
  결합도를 확인한 뒤 복제와 게임 세션 책임을 작은 단위로 분리한다. 소켓 계층 교체는 현재 범위가 아니다.

## 검증 기준

- Client와 Server가 대상 구성에서 빌드되어야 한다.
- 서버 접속, 로비 진입, 게임 시작, 종료 흐름이 유지되어야 한다.
- 네트워크 변경은 패킷 크기, 전송 빈도, 연결 상태를 비교할 수 있어야 한다.
- 네트워크 주기 변경 후 렌더 FPS가 달라도 입력·상태 패킷 빈도가 설정값 범위에 있어야 한다.
- 버그 수정은 재현 조건과 수정 후 결과를 기록해야 한다.
- 성능 개선은 변경 전후 측정값이 있을 때만 완료로 판단한다.
- `architecture.md`, `pipeline.md`, `code_smells.md`와 문서 역할이 겹치지 않아야 한다.
- 각 작업은 독립적으로 검토하고 되돌릴 수 있는 커밋 단위여야 한다.
